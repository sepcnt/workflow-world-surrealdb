# 0.1.1 — Performance Pass

In-depth notes for the 0.1.1 performance migration. The user-facing
CHANGELOG is auto-generated by release-please from the conventional
commits. This file preserves the rationale, trade-offs, and operational
guidance for future reference.

## Why

The 0.1.0 schema and storage layer were a straightforward first pass.
Running the adapter against real workloads surfaced several patterns
where SurrealDB was doing significantly more work than necessary, all
of them fixable in the application layer without touching the SurrealDB
core. The eleven bottlenecks catalogued in `ANALYSIS_OF_PERF.md` fall
into three categories:

1. **Write amplification** — every mutation on the hot tables was also
   producing a changefeed entry, regardless of whether anything was
   going to read it.
2. **Plan regression** — the parameter-OR pattern used for optional
   filters defeated the planner's ability to use the compound indexes
   we'd already defined.
3. **Connection and round-trip overhead** — each stream reader opened
   its own websocket, and bulk deletes were fanned out into N round
   trips instead of a single set operation.

0.1.1 targets items that are squarely in application-layer scope. The
remaining core-level items (per-statement auto-transactions, optimistic
concurrency control, LIVE SELECT inline processing, etc.) stay as
upstream asks against SurrealDB itself.

## Changes

### `schema.ts` — remove CHANGEFEED from hot-write tables

Dropped `CHANGEFEED 3d INCLUDE ORIGINAL` from `workflow_stream_chunks`
and `workflow_queue_jobs`. These are the two tables where every write
really matters: one row per stream chunk, one row per queue mutation.

Per `cf/writer.rs:59-79` every mutation was allocating a
`TableMutation`, cloning the record id, computing a JSON diff for
UPDATEs, and flushing the buffer at commit time. The empirical write
overhead is 30-50% per mutation.

**Verified safe**: LIVE SELECT and CHANGEFEED are independent
subsystems in SurrealDB v3. `core/src/doc/lives.rs` pushes directly to
subscription channels; it does not go through the changefeed writer.
We verified this end-to-end with an ad-hoc test: a table defined
without `CHANGEFEED` still delivers CREATE/UPDATE/DELETE notifications
to a live subscriber correctly. The streamer continues to work.

**Trade-off**: `SHOW CHANGES FOR TABLE workflow_queue_jobs` and
`... workflow_stream_chunks` no longer return any history. No code in
the adapter uses `SHOW CHANGES`; external audit tools that were
relying on it will need to track mutations another way.

**Migration**: the schema uses `DEFINE TABLE IF NOT EXISTS`, so
existing deployments keep their existing changefeed setting. To pick
up the write-latency improvement on a live deployment during a
maintenance window:

```sql
REMOVE TABLE workflow_stream_chunks;
REMOVE TABLE workflow_queue_jobs;
```

then rerun `workflow-surreal-setup`. Destructive: only do this with the
queue drained and all streams closed.

### `storage-helpers.ts` — bulk DELETE for run cleanup

`deleteAllHooksForRun` and `deleteAllWaitsForRun` used to `SELECT * FROM
<table> WHERE runId = $runId`, then loop and issue one `DELETE
thing:id` per row. For a run with 10 hooks that's 11 round trips plus
10 document-lifecycle executions on the delete side.

Replaced with a single set operation:

```sql
DELETE FROM workflow_hooks WHERE runId == $runId;
DELETE FROM workflow_waits WHERE runId == $runId;
```

Same end state, one round trip, one planner invocation, one iterator
pass. Addresses bottleneck #9 (Record-Level vs. Set-Based Operations).

### `storage.ts` — idempotent `run_started`

The SDK's runtime dispatches `events.create('run_started')` on every
queue checkpoint, relying on it as a get-or-start per the runtime.js
contract ("must be idempotent for runs already in 'running' status").
Event sourcing says there is exactly one `run_started` per run, and
the original implementation would write a duplicate row every time.

Short-circuited: when the incoming event is `run_started` and the run
is already in `running` state, return the existing run without
persisting a new event. The synthesized event returned to the caller
uses the original `startedAt` timestamp, so downstream observers see
the consistent "one run, one start" story.

### `list` queries — conditional WHERE assembly

`storage.ts`, `hooks-storage.ts`, `runs-storage.ts`,
`steps-storage.ts`, and `streamer.ts` all had list queries of the form:

```sql
SELECT * FROM <table>
WHERE ($hasRunId == false OR runId == $runId)
  AND ($hasCursor == false OR hookId > $cursor)
ORDER BY hookId ASC
LIMIT $limit;
```

Per `core/src/idx/planner/tree.rs:37-38`, SurrealDB's planner tracks
`all_and` to decide whether a compound index is usable. The
parameter-comparison `OR` branch defeats this: the planner cannot tell
at plan time that the `OR` branch will collapse for a given request,
so it falls back to a full table scan even when a compound index on
`(runId, hookId)` exists.

Replaced with conditional string assembly: build the `WHERE` clause
from only the predicates that are actually set on the request, and
pass only the bindings those predicates reference. The planner now
sees a clean `runId == $runId AND hookId > $cursor` and uses the
compound index. Addresses bottleneck #3 (Dynamic WHERE Patterns
Defeat Index Usage).

### `streamer.ts` — shared live client and fast paths

Three changes in one file:

1. **Shared `LiveRpcClient` across stream readers**. Previously each
   `readFromStream` caller allocated a fresh `LiveRpcClient(config)`
   and opened its own websocket. N concurrent stream consumers meant
   N websockets. Replaced with a ref-counted shared instance: the
   first reader opens the connection, subsequent readers reuse it,
   the last one to release closes it. Addresses bottleneck #10
   (Stream Fan-Out Architecture).

2. **Single-chunk fast path in `writeToStreamMulti`**. For the very
   common case of a single chunk, call the existing `writeChunk`
   directly. For the multi-chunk case, acquire the per-stream lock
   once, persist all chunks inside the lock, then write the stream
   header once at the end. Previously each chunk took the lock
   independently and rewrote the stream header.

3. **Conditional WHERE** in `listChunksAfter` and `getStreamChunks`,
   same rationale as the list query fix above.

### `cli.ts` — local CI default auth fallback

Problem: some CI workflows (including the upstream `workflow` repo's
`e2e-community-world.yml`) have a step ordering where the setup
command runs before the env var step writes `WORKFLOW_SURREAL_*` to
`$GITHUB_ENV`. When `workflow-surreal-setup` ran in that step it saw
no auth in `process.env`, attempted an anonymous connect, and died
with `NotAllowedError: Anonymous access not allowed`.

Fix: when `workflow-surreal-setup` is invoked without auth env vars
AND the target URL resolves to a local hostname (`127.0.0.1`,
`localhost`, `::1`, or unset), fall back to the documented community
world default credentials `root`/`root`. Anything else (non-local
URL, or any non-empty `WORKFLOW_SURREAL_TOKEN` /
`WORKFLOW_SURREAL_USERNAME`) uses the environment as-is and fails
loud if misconfigured.

Localhost detection uses `new URL(raw).hostname` membership in a
fixed set so URLs like `https://evil.com/?x=127.0.0.1` don't
accidentally trigger the fallback.

## What's NOT in 0.1.1

- **Encryption / signing keys / cron**: the experimental
  `workflow-world-surrealdb-next` branch has these, but they were
  incomplete. 0.1.1 is strictly perf + one bug fix; the encryption
  story ships later.
- **Schema migration path for existing deployments**: we intentionally
  keep `DEFINE TABLE IF NOT EXISTS` so upgrades are no-op for the
  schema. Pick up the write-latency win on a live deployment only
  during a maintenance window using the manual `REMOVE TABLE`
  sequence above.
- **queue.ts fetch retry behavior**: unchanged. The fetch / undici
  timeout characteristics observed during `act` testing are a property
  of the test harness, not the adapter.
